# journal — prefab-stage-context

## 2026-07-31 · старт

Повод пришёл из host-проекта: под одну из задач пришлось написать Editor-скрипт
на 934 строки — на `LoadPrefabContents` + `SerializedObject`, единственная причина
существования которого в том, что через MCP нельзя было развести внутрипрефабные ссылки. После сборки
верстки скрипт удалили, но повод остался.

Симптом со стороны использующей модели: `get_selection` возвращает
`Canvas (Environment)/SelectionPanel`, а `get_object` / `get_hierarchy` / `find_gameobject`
на тот же объект отвечают `target not found` / пустым результатом. Причина — `SceneObjects.Roots()`
жёстко брал `SceneManager.GetActiveScene().GetRootGameObjects()`.

## Решение

Резолвинг в кодовой базе оказался централизован: `Resolve` / `ResolvePath` / `All` / `RootNodes` —
все через `Roots()`. Поэтому осведомлённость о стейдже — правка одной функции: `Roots()` →
`TargetScene()`, где `TargetScene()` = сцена открытого стейджа, иначе активная.

Выбор в пользу **неявного** переключения (а не флага `useStage`): так ведёт себя сам Unity — при
открытом стейдже Hierarchy показывает префаб, а объекты сцены недостижимы. Явный флаг заставил бы
модель угадывать, а расхождение с UI редактора порождало бы ровно те же «объект есть на экране, но тул
его не видит». Ценой неявности — поле `context` в ответах, чтобы пустой результат не читался как
«объекта нет».

## Отклонение: `close_prefab` пришлось чинить в этом же таске

Не планировалось. Первый прогон EditMode: **20 падений из 227**, из них 15 — чужие тесты. Разбор
показал каскад: мой тест правит объект внутри стейджа → стейдж становится грязным → `close_prefab`
зовёт `StageUtility.GoToMainStage()` → Unity поднимает `Prefab Has Been Modified` → в batch-режиме
`[Assert] Cancelling DisplayDialogComplex`, стейдж **остаётся открытым** и травит все последующие
тесты (они начинают резолвить в стейдже).

То есть без починки `close_prefab` фичу нельзя даже покрыть тестами. Плюс это ровно тот же класс
проблемы, от которого репозиторий уже защищается в `save_scene` («SaveScene открыл бы модальный диалог
и подвесил главный поток») и в `run_tests scenePolicy`. Интерактивно этот диалог трижды за сессию
вешал главный поток host-проекта на десятки минут — лечится только рукой человека.

Взят тот же словарь политик, что у `run_tests`: `discard` (по умолчанию) | `save` | `abort`.

**Подвох:** публичного API для сброса dirty-флага нет ни в 2022, ни в 6 —
`EditorSceneManager.ClearSceneDirtiness` не компилируется (`CS0117`). Пошли рефлексией по internal
(`PrefabStage.ClearDirtiness`, фолбэк `EditorSceneManager.ClearSceneDirtiness`) — прецедент в коде уже
есть, `ScreenshotTool` так же берёт размер Game View. Если ни один метод не найден — тул **отказывает
с внятной ошибкой**, а не проваливается в модалку.

## Верификация

- EditMode-набор целиком (`TestProject~`, headless CLI, Unity 2022.3.62f2), не только новые тесты —
  ради регрессий от правки `Roots()`, через которую ходит вся объектная адресация.
- Новые тесты — на **реальном** `PrefabStage`, без моков: переключение контекста туда и обратно,
  принадлежность созданного объекта `stage.scene`, `parent` у `instantiate_prefab` (в т.ч. что при
  неизвестном родителе инстанс не создаётся), три политики `close_prefab`.
- Ловушка в `SetUp`: одноимённый объект кладётся в активную сцену — проверяет, что резолв не
  сваливается обратно в сцену, когда в стейдже совпадения нет.

## 2026-07-31 · результат

EditMode целиком: **229/230**, все 10 новых тестов зелёные. Единственное падение —
`RegistryStoreConcurrencyTests.Concurrent_Upsert_KeepsAllInstances`, вне зоны правки; прогнан
отдельно — проходит, то есть флак под нагрузкой (в момент прогона было запущено три инстанса Unity),
а не регрессия.

Промежуточные грабли, стоившие двух прогонов: `EditorSceneManager.ClearSceneDirtiness` не существует
как публичный API (`CS0117`) → ушли в рефлексию; `using System;` в `PrefabTools.cs` даёт `CS0104`
(`Object` — неоднозначность с `UnityEngine.Object`, который там уже используется) → квалифицировали
`System.Type` / `System.Exception` точечно. Ещё один тест падал не из-за тула: `GameObject.Find` не
видит объекты preview-сцены стейджа — проверка переписана на обход `stage.scene.GetRootGameObjects()`.

Прогон делался редактором `2022.3.62f2` (в системе нет `f3`, на котором заведён `TestProject~`) —
наведённый дрейф `ProjectVersion.txt` / `ProjectSettings.asset` откачен, в коммит не попал.
