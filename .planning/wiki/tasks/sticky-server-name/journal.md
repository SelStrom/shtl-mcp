# journal — sticky-server-name

## [2026-08-03] Диагностика

Повод пришёл из практики, а не из кода: агент работал в одном checkout'е проекта,
собрался прогнать C# через `run_csharp`, проверил `status` и увидел чужой
`projectPath` — соседний checkout того же проекта. Дальше — разбор, почему
инструменты с «главным» именем ведут не в главный checkout.

Собранная картина (реестр + живые `status` по портам): два инстанса одного продукта,
у первого по времени старта — базовое `unity-<product>`, у поднятого позже —
`unity-<product>-<hash4>`. Порт у обоих детерминирован по пути и стабилен, имя — нет:
голое досталось тому, кто раньше стартовал. `Application.productName` у клонов
одинаков, поэтому претендуют все.

Дополнительно выяснилось (важно для дизайна фикса): реестр **никогда не чистится** —
`Prune` вызывается только из тестов, у `Remove(projectPath)` нет вызовов в проде.
Наблюдаемо: запись давно закрытого инстанса жила в реестре третьи сутки. Значит
`registry.json` — durable-карта `projectPath → serverName`, и закрепление имени не
требует нового хранилища.

## [2026-08-03] Решение и реализация

Рассмотрены три варианта; выбран «липкое имя» как единственный обратносовместимый:

1. **Имя из папки для всех** — переименовывает даже одиночные установки, у которых
   коллизии никогда не было. Отклонён.
2. **Только читаемый суффикс** (hash4 → папка) — минимальная правка, но корневая
   нестабильность голого имени остаётся, а инстансы с hash-суффиксом переименуются.
   Отклонён.
3. **Липкое имя** (принято) — имя закрепляется за путём, миграция бесплатная, потому
   что источник закрепления (реестр) уже содержит имена всех запускавшихся инстансов.

Код: `ServerName.Resolve` получил необязательный `assignedName`; минт выделен в
`Mint` с тремя ступенями (базовое → папка → hash4); `RegistryStore.NameForPath`;
проброс в `ShtlMcpServer.EnsureStarted`.

Читаемая средняя ступень добавлена сюда же: она срабатывает только при минте нового
имени, то есть никого не переименовывает, а новые worktrees получают
`unity-<продукт>-<папка>` вместо хеша.

## [2026-08-03] Верификация

- Standalone-прогон логики `Resolve` вне Unity (копия `ServerName.cs` + `Fnv.cs` в
  консольный хост): **14/14**. Покрыты 4 существующих кейса без изменений, 6 новых и
  4 кейса на путях реальной multi-checkout установки — оба живых инстанса сохраняют
  текущие имена, гипотетический новый checkout получает читаемое имя по папке.
- Компиляция Editor-сборок — в живом редакторе host-проекта, куда пакет подключён
  junction'ом: домен перезагрузился, listener переподнялся, консоль чистая. Инстанс
  после reload сохранил своё имя (реальная проверка миграции на живой установке).
- **Не выполнено:** EditMode-прогон `ServerNameTests`/`RegistryStoreTests` в Unity —
  тестовая сборка ограничена `defineConstraints: SHTL_MCP_DEV`, а инстанс
  `TestProject~` не поднят (запуск Unity вне зоны MCP). Прогон — за ревьюером.
