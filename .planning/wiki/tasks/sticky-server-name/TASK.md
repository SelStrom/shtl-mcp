# TASK: serverName закрепляется за путём проекта (стабильный адрес инстанса)

**Status:** in review
**Тип:** forward (raw → wiki → code): меняется намерение об уникальности имени —
из «уникально среди живых» в «уникально и закреплено за путём».
**Привязка:** F1 (AC1.3 переформулирован, добавлен AC1.8), INV-3 (однозначность
инстанса), wiki/multi-instance.md §Имя сервера.

## Проблема (как всплыло)

На машине с несколькими checkout'ами одного Unity-проекта модель-потребитель пошла
править код в одном из них, а инструменты с базовым префиксом привели её в другой:
голое имя держал инстанс, который просто стартовал раньше, а checkout, где шла
работа, поднялся позже и получил имя с hash4-суффиксом.

Корень — `ServerName.Resolve` вычислял имя **на каждом старте** из того, кто в этот
момент жив:

```csharp
baseName = "unity-" + Sanitize(productName);
existing = livePathForName(baseName);          // живой = heartbeat ≤ 30 c
if (existing == null || existing == projectPath) return baseName;
return baseName + "-" + Fnv.Hash4(projectPath);
```

То есть базовое имя — **аренда по порядку запуска**, а не свойство checkout'а. Два
следствия:

1. `Application.productName` у всех клонов одинаков, поэтому на голое имя претендуют
   все — кому достанется, решает случайность порядка открытия Unity.
2. Клиентская запись `claude mcp add` ключуется именем и переживает рестарты (AC1.5),
   а имя — нет. Закрыть первый инстанс и перезапустить второй достаточно, чтобы
   `unity-<product>` на стороне Unity начал означать другой проект: реестр и
   control-флаг `~/.unity-mcp/<serverName>.cmd` уедут на новое имя, а запись в
   конфиге клиента останется смотреть на старый порт. Повторное добавление из
   дашборда даст второе имя на тот же инстанс.

Порт от этого не страдал — он детерминирован по пути (AC1.4). Асимметрия «порт
стабилен, имя нет» и есть баг намерения: адрес инстанса состоит из обоих.

## Решение

Имя назначается один раз и хранится там, где и так живёт идентичность инстанса — в
`registry.json`:

- `RegistryStore.NameForPath(projectPath)` — имя из записи этого пути, **без TTL**.
  Записи durable: `Prune` вызывается только из тестов, у `Remove` нет вызовов в проде,
  поэтому запись переживает остановку Unity и служит носителем закрепления.
- `ServerName.Resolve(..., assignedName)` — если имя уже закреплено, возвращает его и
  ничего не вычисляет.
- Минт нового имени (только для незнакомого пути): базовое → имя папки → hash4.
  Средняя ступень новая: имя папки читается, хеш пути — нет.

## Обратная совместимость

Полная для всех, кто уже поднимался: запись в реестре есть → имя берётся из неё →
не меняется ни у кого. Проверено на реальной multi-checkout установке: оба живых
инстанса сохранили свои имена (базовое и суффиксное), записи в конфиге клиента
остались валидны, дублей не появилось.

Единственный сценарий смены имени — удалённый или впервые созданный `registry.json`:
имена переминтятся как на чистой машине. Это то же поведение, что и сегодня.

## Acceptance

- **A1** — Инстанс, уже имеющий запись в реестре, сохраняет имя независимо от того,
  какие инстансы подняты сейчас (в т.ч. когда базовое имя свободно).
- **A2** — Новый путь при занятом базовом имени получает `unity-<имя папки>`.
- **A3** — Если имя папки совпадает с базовым или тоже занято — hash4-суффикс
  (прежнее поведение).
- **A4** — Поведение без закреплённого имени не изменилось: существующие тесты
  `ServerNameTests` проходят без правок.

## Верификация

- `ServerNameTests` — 4 существующих + 6 новых кейсов (A1–A4).
- `RegistryStoreTests.NameForPath_IgnoresHeartbeatAge` — закрепление не зависит от
  свежести heartbeat.
- Логика `Resolve` дополнительно прогнана вне Unity (standalone-хост, 14/14),
  включая пути реальной multi-checkout установки.
- EditMode-прогон в Unity **не выполнялся**: тестовая сборка под
  `defineConstraints: SHTL_MCP_DEV`, инстанс `TestProject~` не поднят. Нужен прогон
  ревьюером.
