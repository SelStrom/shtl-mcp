# tasks/ — история тасков

История работы по таскам. Один таск = одна папка `wiki/tasks/<task-slug>/`.
Slug — короткий kebab-case (напр. `transport-jsonrpc`, `registry-heartbeat`,
`dashboard-mvp`).

## Что внутри `<task-slug>/`
Свободный, но консистентный набор markdown-артефактов:

- `TASK.md` — цель таска, привязка к raw-фичам (F1..F6) и wiki-системам,
  acceptance, план шагов, статус.
- `journal.md` — append-only ход работы: что сделано, отклонения, решения,
  результаты верификации (тесты/ручная проверка).
- (опц.) `notes.md`, скриншоты, выдержки исследований — что нужно для контекста.

## Гигиена публичного репозитория

**Сторонние проекты не упоминаются — ни реальные, ни вымышленные**, в том числе как
примеры. Это касается `TASK.md`, `journal.md` и любых заметок таска.

Повод и контекст задачи описываются обезличенно: «host-проект», «проект-потребитель»,
«установка с несколькими checkout'ами». Не приводятся названия проектов, ключи задач
трекера, имена их файлов, размеры и цитаты их кода. Ценность записи в том, *что*
всплыло и *почему*, а не в том, у кого именно.

## Связь с общим флоу
- Существенные изменения поведения проходят сначала через `raw/` (см. CLAUDE.md,
  forward-поток). Таск ссылается на затронутые raw-фичи и wiki-страницы.
- По завершении: обновить `wiki/index.md` (если появились code-страницы),
  дописать `wiki/log.md` строкой `forward | <фича> | <таск-slug>`.
- `wiki/code/` пополняется reference-страницами по реализованному коду (с pin к
  коммиту) — это и есть дешёвый структурный контекст для будущих операций.
