# F2 — Конфигурация и перезапуск/health

**Требование #2.** Лёгкая понятная настройка и конфигурация; модель естественно
восстанавливает связь, если MCP отвалился или недоступен.

Решение по объёму восстановления (зафиксировано): **watchdog внутри Unity +
reconnect + control-flag** (LLM-инициируемый форс-рестарт через файл). Запуск
самого Unity моделью и внешний демон — отвергнуты.

## Acceptance criteria

- **AC2.1** — Конфиг (диапазон портов, авто-старт, интервал heartbeat,
  включение/выключение «опасных» инструментов вроде `run_csharp`) — в одном
  месте (ProjectSettings-asset или EditorPrefs), редактируется из дашборда.
- **AC2.2** — Сервер переживает domain reload и play/edit-переход автоматически
  (watchdog переподнимает listener; детали — F4).
- **AC2.3** — При сбое вызова модель следует документированному флоу: читает
  реестр (жив ли инстанс) → `claude mcp` reconnect. Флоу зафиксирован в CLAUDE.md.
- **AC2.4** — Дашборд имеет кнопку ручного **Restart server** (force respawn).
- **AC2.5** — Unity закрыт/завис → запись в реестре протухает по `lastHeartbeat`;
  восстановление самого инстанса вне зоны MCP (человек открывает Unity).
- **AC2.6** — Control-flag канал: модель через Bash пишет управляющий флаг
  `~/.unity-mcp/<serverName>.cmd` (напр. `restart`); watchdog на ближайшем тике
  главного потока исполняет его (форс-пересоздание listener, даже если тот завис)
  и удаляет флаг. Канал работает, когда HTTP-сервер недоступен; ноль внешних
  процессов; Unity не запускается.
- **AC2.7** — Recovery playbook: в `CLAUDE.md §Recovery` зафиксировано
  детерминированное дерево восстановления для использующей модели (вызов упал →
  читать реестр → pid жив → write restart-flag → reconnect; pid мёртв → Unity
  закрыт, вне зоны MCP). При реализации playbook дублируется в подсказках ошибок
  инструментов и описании `status`.

## Out of scope
- Авто-запуск/перезапуск процесса Unity моделью.
- Любой фоновый процесс-супервизор вне Unity.
