# Мульти-инстансовость и discovery

Цель: несколько Unity-инстансов сосуществуют, и модель детерминированно адресует
команды нужному (INV-3). Без роутера/брокера — чисто и отказоустойчиво.

## Факт-ограничение
Unity лочит папку проекта (`Temp/UnityLockfile`) — один и тот же путь нельзя
открыть дважды. Значит «несколько инстансов одного проекта» = **разные пути**:
клоны или **git worktrees** (отдельный рабочий каталог → отдельный путь).

## Порт
`port = base + (hash(projectPath) mod range)`, диапазон напр. `9700..9799`. При
занятости — следующий свободный. **Реальный порт пишется в реестр** (реестр —
истина). Свойство: порт стабилен по пути между рестартами Unity → ранее
добавленная `claude mcp add`-запись продолжает работать.

## Имя сервера (serverName) — ключ однозначности
- По умолчанию `unity-<projectName>` (projectName из `Application.productName`
  или имени папки).
- При обнаружении в реестре **другого живого** инстанса с тем же именем и другим
  путём → суффикс коротким хешем пути: `unity-<projectName>-<hash4>`
  (напр. `unity-PerfectWar-a3f9`).
- Одиночный обычный случай остаётся «красивым»; клоны/worktrees — однозначно
  различимы. Дашборд всегда показывает фактическое имя и точную строку
  подключения.

## Реестр `~/.unity-mcp/registry.json`
Массив записей живых инстансов; каждый инстанс владеет своей записью и обновляет
heartbeat:

```json
{
  "id": "uuid",
  "projectName": "PerfectWar",
  "projectPath": "/Users/.../PerfectWar",
  "unityVersion": "2022.3.x",
  "serverName": "unity-PerfectWar",
  "port": 9712,
  "pid": 12345,
  "mode": "edit",
  "compiling": false,
  "startedAt": "2026-06-13T12:00:00Z",
  "lastHeartbeat": "2026-06-13T12:03:00Z"
}
```

- Heartbeat обновляется по таймеру; запись с протухшим `lastHeartbeat`
  (старше порога) считается мёртвой и игнорируется/чистится.
- Запись на диск — атомарная (tmp + rename), чтобы не словить гонку при
  нескольких инстансах.
- Тот же каталог `~/.unity-mcp/` хранит управляющие флаги `<serverName>.cmd`
  (см. `lifecycle-and-reload.md` §4 Control-channel).

## Как модель адресует инстанс
1. `cat ~/.unity-mcp/registry.json` (Bash) → видит все живые инстансы и порты.
2. `claude mcp add --transport http <serverName> http://127.0.0.1:<port>/mcp`
   для нужных.
3. Инструменты приходят с префиксом `mcp__<serverName>__*` → **префикс = адрес
   инстанса**. Действие над другим инстансом = вызов его префиксованных
   инструментов.
4. Любой ответ инструмента и `status` несут `projectName` → постоянная сверка.

## Scope регистрации (по умолчанию — user-level)
- **user-level** `~/.claude.json` (`-s user`) — рекомендовано: нулевой след в
  репо (INV-2), корректно при динамическом порте и worktrees.
- **project-level** `.mcp.json` (`-s project`) — документированная опция;
  **хрупка**: закоммиченный URL неверен на другой машине и для worktree-ов
  (у них разные порты при одном файле). Подходит только для строго одного
  фиксированного инстанса.
- Scope малозначим по сути: реальное подключение — живой флоу «реестр → дашборд
  даёт готовую команду → модель регистрирует on-demand», а не статичный URL.

## Worktrees — нюанс Unity (информационно, не задача MCP)
Worktrees не делят `Library/` — каждый переимпортирует ассеты. MCP это
безразлично: он видит разные пути.
